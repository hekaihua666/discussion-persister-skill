# 讨论持久化

将本窗口的学习讨论整理为准确、直白、便于复习的一问一答。只处理本次新增讨论，旧题按需局部更新。

## 触发与文件

- 按意图识别“保存这段讨论”“整理到笔记里”“更新一下笔记”等表达，不依赖固定口令。
- “Redis 怎么做持久化”“这个 skill 怎么优化”属于问答或维护任务，不是保存命令。指代明确时直接执行；只有保存对象或目标确实不清楚时才简短询问。
- 相对路径均以包含本 skill 的项目根目录为基准，不随终端当前目录改变。

| 文件 | 默认路径 |
|---|---|
| 笔记 | `Java八股文讨论笔记.md` |
| 光标 | `.dsh/discussion-cursor.json` |

一个窗口默认对应一个笔记。用户明确要求新建时，采用其指定名称；未指定则使用有意义且不覆盖现有文件的名称。新笔记建立独立光标（如 `.dsh/discussion-cursor-2.json`），批次数从 0 起、题号从 Q1 起，旧文件保留；沿用当前进度还是重新整理历史，以用户要求为准，未说明时沿用已确认边界。

## 光标约定

```json
{
  "schemaVersion": 2,
  "conversationId": null,
  "conversationTitle": "Java八股文讨论",
  "noteFile": "Java八股文讨论笔记.md",
  "lastBatchAt": null,
  "batchCount": 0,
  "lastTopic": null,
  "lastProcessedBoundary": null
}
```

- `conversationId`：环境实际提供的稳定会话 ID；没有就留 `null`。优先检查环境变量（如 `DSH_SESSION_ID`）或宿主 API 是否提供会话级标识，其次使用窗口标题或已知上下文中稳定且可跨轮次识别的会话标签；标题仅作辅助，不能当作唯一身份。
- `noteFile`：绑定的笔记相对路径。其他窗口不得直接套用这份光标；无 ID 时，先根据窗口与已知上下文确认归属，不能只凭同名话题判断。
- `lastBatchAt`、`batchCount`：最近一次讨论保存成功修改笔记的时间、累计修改批次数；只更新光标或单独维护笔记不增加批次。
- `lastTopic`：最近一次写入或更新的题目标题，仅供辅助查找。
- `lastProcessedBoundary`：最近一次完整处理到的保存命令。记录实际可用的 `messageId`、`triggerText`（命令原文）、`precedingExchange`（相邻一组问答的简短非敏感摘录）；不存在的字段用 `null`。优先用真实消息 ID，无 ID 时使用原文与相邻问答共同定位，须能唯一匹配。
- 不编造消息 ID、消息时间、完整历史或提问次数。执行时间来自环境，并保留时区。
- 迁移旧光标时，保留原时间、批次数和话题；缺失字段补 `null`，不要把迁移操作当作一次保存，也不要把当前维护命令填成历史边界。

#### 版本迁移

读到旧版本光标时按以下规则兼容，不因升级丢失进度：

- `schemaVersion: 1`：字段可能缺少 `conversationId`、`noteFile`、`lastProcessedBoundary`。保留 `batchCount` 和 `lastBatchAt`（值的含义不变）；缺失字段补 `null`。不因迁移重算批次或改写历史边界。
- 无 `schemaVersion`：当作 v1 处理。
- 迁移后的光标仍以本次扫描的完整处理结果为准推进；迁移操作本身不增批次数、不写保存凭据。

#### 光标初始化：笔记已有内容时

笔记文件已存在但光标缺失的情况（例如手动创建了笔记或光标被误删），不能简单从 `batchCount: 0` 开始：

1. 读笔记文件末尾的 HTML 保存凭据（`<!-- discussion-persister: ... -->`）。
2. 如果凭据存在且可解析，从中恢复 `batchCount`、`lastTopic` 和 `boundary`，以此重建光标。
3. 如果保存凭据也不存在，则：
   - `batchCount` 取笔记中最大批次号（如果识别不到批次号，保守设为当前可见批次数）。
   - `lastProcessedBoundary` 设为 `null`（无法定位上次边界，下次保存时按"边界缺失"处理）。
4. 恢复的光标记 `"rebuiltFromNote": true` 及恢复时间，以备后续核对。

## 每次保存的流程

### 1. 读取并确认范围

读取光标与已有笔记，先浏览题目及重复标记，再细读相关答案。核对会话与目标文件后，确定扫描区间：**上次已确认保存命令之后，到本次保存命令之前**。两条命令本身不记为知识问答。

- 环境提供历史读取工具或用户提供聊天导出时，按需读取待处理区间；skill 本身不提供历史访问能力。
- 光标不存在时，整理当前实际可读取的历史；若只覆盖部分历史，明确说明范围，不称为完整归档。只有确认从会话起点到本次命令连续可读时，才建立完整处理光标；用户明确指定从某处起记，也可从该处建立边界。
- 旧光标只有时间与话题时，必须结合原始对话找到对应保存命令；时间、话题或压缩摘要不能单独确定边界。
- 边界缺失、匹配到多处，或待处理区间中间有缺口时，不自动改成全量重扫。说明缺失范围，请用户提供对应聊天导出或明确新的记录起点；未解决前保留旧光标。
- 用户要求先保存确定可见的部分时可以执行，但标注覆盖范围与缺口，不跨越缺口推进完整处理光标；已有题只补必要内容，重复标记采用“多次讨论”，不累加精确次数。
- **部分保存连续出现时**：两次部分保存的覆盖区间不自动合并，各自的缺口独立标注。只有用户明确说“把前面几段缺的也补上”或提供缺失区间的导出，才将多次部分保存的区间拼成一段完整处理并推进 `lastProcessedBoundary`。
- 压缩摘要只用于理解背景，不作为原始消息位置或精确次数的证据。

### 2. 筛选讨论

保留 Java 及相关学习主题的技术问答，包括 JVM、集合、并发、框架、数据库，以及为理解这些问题展开的 C、Python 等对比。

跳过礼貌确认、无关闲聊、纯操作指令、本 skill 的维护过程，以及用户明确要求“不要记”的内容。不写入密码、token、API key、私人账号或未脱敏日志；边界摘录和保存标记同样遵守这一要求。

“没听懂，讲直白一点”归入原题；追问若改变适用范围、讨论不同机制或可独立复习，可另成一题，不能因关键词相同就强行合并。

### 3. 归并与重复标记

按**问题意图、对象和适用范围**判断是否同题，不只匹配措辞。例如“JDK/JRE/JVM 分别是什么”和“三者有什么关系”可以合并；“HashMap 如何扩容”和“ConcurrentHashMap 如何扩容”应分别记录。

- 同一轮澄清、换种讲法、深入追问不算再次提问。
- 用户在后续独立讨论中再次提出同一问题，才增加重复次数；同一新增区间内独立重复提出也按此处理。
- 原始历史完整且总次数可核对时，题目后标 `（累计提问 N 次）`。旧笔记没有次数标记，不等于历史只问过一次。
- 确认重复但历史次数不完整时，标 `（多次讨论）`；不要把后来可见的次数写成历史总次数。
- 再次保存同一段历史不重复计数；单次出现的题目不强制加次数标记。

| 情况 | 写入方式 |
|---|---|
| 新问题 | 在末尾追加新 QA |
| 重复问题，无新增信息 | 仅更新原题重复标记 |
| 同题有必要补充 | 局部补充原答案，保留题号 |
| 已有事实错误 | 局部纠正，并在汇报中说明题号和改动 |
| 只是润色、重排或换个比喻 | 保持原样 |

不在新批次中再次追加旧题全文；不重排、不重新编号旧题。

### 4. 精简与核实

- 问题压缩为一两句话，保留原意；回答先给核心结论，再给必要解释或例子。
- 删除客套、重复和离题内容；不擅自按“面试不考”删除用户实际讨论的知识。
- 类比有帮助时保留，随后给出准确含义；不凭空添加用户的学习偏好。
- 保留版本、实现和使用条件，例如 Java 8 与模块化 JDK、JVM 规范与 HotSpot、Python 与 CPython。
- 对记忆不确定、争议，以及版本变更、性能或许可结论，按需核对官方规范、文档或发布说明；关键结论在对应 QA 附简短来源，不要求每题机械堆链接。
- 缺少可靠依据时保留限定、去掉未经核实的断言，或标“待核实”；不要为了让笔记完整补写猜测。
- 正文呈现纠正后的知识，不堆修改历史；本次汇报说明修正了什么。

### 5. 写入、检查、推进光标

新题全局连续编号；新题所在批次格式：

```text
---

## 批次 N（实际执行日期与时间，含时区）

### Q8: 本次新增问题

**A:** 先给结论，再用必要解释展开。
```

1. 先确定新增、同题补充、重复标记与纠错的最小改动范围，再写笔记。
2. 有笔记改动时，在文件末尾留一条 HTML 注释作为保存凭据，包含修改批次号和本次命令的边界对象，格式为 `<!-- discussion-persister: {"batchCount": N, "boundary": {...}} -->`；其中值必须替换为实际值。仅更新旧题时只留凭据，不建立空的可见批次。部分保存另加 `"partial": true`，与完整保存区分。
3. 写入后重读受影响条目与保存凭据，核对题号、重复标记、内容及未涉及旧题；成功后才写光标。写入失败不推进光标。
4. 本次保存有笔记改动时，更新修改时间、批次数和最后题目；完整处理成功才将 `lastProcessedBoundary` 更新为本次命令，部分保存保持旧边界。没有新内容时不改笔记、不增批次，可以推进已完整检查的边界。
5. 重试前比较光标、保存凭据与本次扫描区间：已保存的区间不再次写入或累计次数。若笔记已保存、光标未更新，且凭据可唯一定位并确认该区间完整处理，仅补齐光标；部分保存凭据不用于跨缺口推进光标。匹配含糊时先定位，不猜测。

用户单独要求纠正笔记或维护 skill 时，只做指定维护，不把该操作当作新讨论保存或推进讨论边界；相关维护也不增加讨论批次数。

### 6. 简短汇报

报告实际处理范围、新增 QA 数、补充旧题数、更新重复标记数和纠错题号；无变化项可省略。附笔记路径；历史有缺口或部分条目待核实时明确指出。不要宣称保存了实际没有读取到的历史。

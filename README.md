# discussion-persister skill

一个把「聊天里的学习讨论」沉淀成复习笔记的 Agent Skill。

`discussion-persister` 让 AI 在你下一条命令时，回看**上次保存命令之后**的新讨论，过滤掉闲聊，把技术问答精简成一问一答，写进一个 Markdown 笔记。第二天回来接着聊，再下一次命令，它会在原有笔记上做**最小增量更新**，而不是从头重写。

它回答的其实就一个问题：

> 我们上次聊到哪了，这次新学的东西记哪儿？

## 为什么需要它

在 AI 对话框里学东西，最大的问题是**记录会没**：

- 对话被误删、上下文被压缩，之前问过的知识点就找不回来了。
- 同一道八股题反复问，但没人帮你合并成一条。
- 想复习的时候，翻几百轮聊天记录效率极低。
- `README.md` 是给项目看的，`AGENTS.md` 是给规则看的，都不是「我学过的知识点」。

这个 skill 给 AI 一个固定的落盘位置和固定的更新规则，让学习记录变成真正的文件资产。

## 什么时候触发

会触发：

- 「把这段讨论保存一下」「整理到笔记里」「更新一下笔记」
- 任何语义上表达「把刚才聊的知识点记下来」的说法

不会触发：

- 普通知识问答（问了就答，不写文件）
- 询问持久化技术本身（比如「Redis 怎么做持久化」）
- 评审或修改这个 skill 的过程

触发靠**意图识别**，不是固定口令。所以你可以自然地说「帮我存一下」或者「整理进笔记吧」，都算。

## 安装

把 `discussion-persister/` 整个文件夹放进项目的 skills 目录：

```text
<项目根目录>/.dsh/skills/discussion-persister
```

Windows 示例：

```text
C:\Users\<username>\Desktop\my-project\.dsh\skills\discussion-persister
```

装好后，Agent 会读取 `discussion-persister/SKILL.md`，靠 frontmatter 里的 `description` 判断什么时候该用。

## 默认文件

| 文件 | 默认路径 | 作用 |
|---|---|---|
| 笔记 | `Java八股文讨论笔记.md` | 给人看的复习资料，一问一答 |
| 光标 | `.dsh/discussion-cursor.json` | 给 AI 看的进度书签 |

两个文件都在**项目根目录**下，与终端当前目录无关。

一个对话窗口默认对应一个笔记。只有你明确说「新建一个笔记」，才会用你给的名字建新文件、建独立光标（如 `.dsh/discussion-cursor-2.json`），旧文件保留。

## 光标结构

```json
{
  "schemaVersion": 2,
  "conversationId": null,
  "conversationTitle": "Java八股文讨论",
  "noteFile": "Java八股文讨论笔记.md",
  "lastBatchAt": "2026-11-05T22:20:00+08:00",
  "batchCount": 1,
  "lastTopic": "Q7: C、Java、Python 编译vs解释对比",
  "lastProcessedBoundary": {
    "messageId": null,
    "triggerText": "保存一下这段讨论",
    "precedingExchange": "Q: C 和 Java 谁快？ A: 看实现和场景……"
  }
}
```

几个关键字段：

- `lastProcessedBoundary`：上次**完整**处理到哪条保存命令。优先记真实 `messageId`，没有就用命令原文 + 相邻一组问答定位。
- `batchCount`：累计保存批次数。只改光标、只维护旧题都不加批次。
- `schemaVersion`：目前是 2。读到 v1 会自动迁移，不丢进度。
- `conversationId`：环境给得出就填，给不出留 `null`。标题只做辅助，不能当唯一身份。

有个配套设计：**笔记末尾有一条 HTML 保存凭据**

```html
<!-- discussion-persister: {"batchCount": 3, "boundary": {...}} -->
```

哪怕光标文件被误删，也能从笔记里把批次号和边界恢复出来。光标和笔记互为备份。

## 保存流程

每次你说「保存一下」，走这六步：

### 1. 读取并确认范围

读光标 + 读笔记，先扫一遍题目和重复标记，再细读相关答案。

确定扫描区间：**上次已确认的保存命令之后，到这次保存命令之前**。两条命令本身不算知识问答。

边界模糊、匹配到多处、中间有缺口时，**不擅自改成全量重扫**。会告诉你缺哪儿，请你补导出或指定新起点，在那之前保留旧光标。

### 2. 筛选讨论

保留 Java 及相关技术问答（JVM、集合、并发、框架、数据库，以及为讲清楚问题而展开的 C、Python 对比）。

跳过：客套、闲聊、纯操作指令、skill 自身的维护过程，以及你说「这个别记」的内容。

不写入密码、token、API key、私人账号、未脱敏日志。

### 3. 归并和重复标记

按**问题意图、对象、适用范围**判断是不是同一题，不是只看措辞：

- 「JDK/JRE/JVM 分别是什么」和「三者什么关系」→ 合并
- 「HashMap 怎么扩容」和「ConcurrentHashMap 怎么扩容」→ 分开

重复处理：

| 情况 | 写入方式 |
|---|---|
| 同一轮里的澄清、换种讲法 | 不算再次提问 |
| 后续独立讨论中又问了一次 | 增加重复次数 |
| 总次数能核对 | 标 `（累计提问 N 次）` |
| 次数不完整 | 标 `（多次讨论）`，不瞎编历史总数 |

### 4. 精简与核实

- 问题压成一两句，保留原意。
- 回答**先给结论**，再补必要解释或例子。
- 删客套、删重复、删离题；但不按「面试不考」擅自删你实际讨论过的知识。
- 保留版本、实现、使用条件（Java 8 vs 模块化 JDK、JVM 规范 vs HotSpot 实现、Python vs CPython）。
- 对版本变更、性能、许可这类容易过时的结论，按需核对官方文档，在对应 QA 附简短来源。
- 缺可靠依据时保留限定、去掉没核实的断言，或者标「待核实」。
- **发现之前讲错了，直接改对，正文不留修改痕迹**，只在汇报里说改了哪题。

### 5. 写入、检查、推进光标

写入顺序是固定的，防止半途失败留下不一致状态：

1. 先确定最小改动范围（新增 / 同题补充 / 重复标记 / 纠错）。
2. 写笔记，末尾更新那条 HTML 保存凭据。
3. **重读**受影响条目和凭据，核对题号、标记、内容，以及旧题有没有被误改。
4. 检查通过后，才写光标。写入失败不推进光标。
5. 下次重试前，先比对光标、凭据和扫描区间：已保存的区间不重复写、不重复计数。

### 6. 简短汇报

告诉你：处理了哪个区间、新增几道题、补充几道旧题、更新几个重复标记、纠正了哪几题。有缺口或待核实的会明说。

## 更新原则：非必要不改

这是整个 skill 最核心的一条约束。

- 新题只在**末尾追加**，全局连续编号。
- 旧题**不重排、不重新编号、不重写**。
- 只是润色、换比喻、调整顺序的，一律保持原样。
- 同题有新信息才局部补充，保留原题号。
- 旧题有事实错误才改，而且只改错的地方。
- 不在新批次里再次追加旧题全文。

道理很简单：笔记是给你复习用的，位置老变你就记不住了。

## 体积与质量

- 笔记是知识点集合，不是聊天记录转储。只记问答，不记过程。
- 回答够用就行，不堆砌。
- 类比可以留，但后面必须给出准确含义。
- 不凭空添加你的学习偏好。
- 压缩摘要只用来理解背景，不作为「原始消息位置」或「提问次数」的证据。

## 设计取舍

几个当初纠结过、最后定下来的点：

**为什么不用消息 ID 当主锚点？**
很多 Agent 运行环境拿不到稳定的消息 ID。所以光标以「上次保存命令」这个语义边界为主，消息 ID 有就记、没有就不记。

**为什么笔记里要藏一条 HTML 注释？**
光标是单独的文件，会丢。笔记末尾的凭据是同一份信息的副本，两边互为兜底。

**为什么第二次只扫增量？**
每次全量重扫既慢又容易重复计数，还可能导致旧题被改写。增量扫描 + 最小改动，才符合「复习资料要稳定」的直觉。

**为什么不写死命令词？**
固定口令很脆。用意图识别，「保存一下」「记下来」「整理进笔记」都能触发，也不会误伤普通问答。
